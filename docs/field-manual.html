How the pieces fit before you touch any one of them

KM Finny runs a physical warehouse: CSV orders come in, staff scan boxes against them on the floor, stock totals move, and paperwork (vouchers, slips, dispatch labels) gets printed along the way. Every module below either produces data the others read, or consumes data another module produced — Order Management feeds Order Scan, Order Scan feeds Overall Stock and Order Reports, Product Master feeds product data to all of them.

Three separate mechanisms gate what a person can see and do, layered on top of each other. Role (admin / super-admin / read/write / read) is global and coarse — admins bypass every other check. Allowed Pages (users.allowedPages, a JSON array of page keys) is per-user and controls which pages even render for someone who isn't an admin. Write Access (users.pageWriteAccess, a subset of Allowed Pages) controls whether a non-admin can edit or only view a page they can already see. All three are set from User Management. A handful of pages layer a fourth, older mechanism on top — department-name string matching (e.g. "DISPATCH {VALSAD}") — which predates the page-key system and still drives a few pages noted below.

Login & Sessions

client/src/pages/Login.tsx

Everyone's entry point. A 4-digit PIN pad, not a username/password form — built on Passport's LocalStrategy underneath, with the PIN riding in as the "password" field.

No login required to view this page Table: users

How it works

  1. User taps four digits on the on-screen pad (or types them on a physical keyboard — the page listens for keydown events directly, no hidden input field).
  2. On the fourth digit it auto-submits — no explicit "Log in" tap needed.
  3. The server tries, in order: PIN 9999 as a hardcoded emergency admin bypass; a PIN-only lookup across every user (rejecting common PINs like 0000/1111/1234 unless a username is also given, and rejecting the login outright if two people share the same PIN); then a normal username lookup.
  4. On success, the full user record lands in React Query's cache and a trimmed copy (role, department, plants, allowedPages, pageWriteAccess) is written to localStorage['currentUser'] — this is what every page's client-side permission check actually reads.
  5. Logging out clears the session server-side and wipes four localStorage keys, then returns to the PIN pad.

API & session mechanics

POST/api/loginbody: { username: "pin-login", password: <pin> }
GET/api/usercurrent session's user; Cache-Control: no-store so a permission grant is never served stale
POST/api/logout

Sessions are identified by userCode (the stable employee code), not the numeric row id — server/auth.ts's serializeUser/deserializeUser re-reads the user fresh from Postgres on every request, so a permission change made in User Management is live on that person's very next request, no re-login needed. Passwords/PINs are hashed with scrypt; a legacy plaintext PIN is silently upgraded to a hash the first time it's used successfully. Cookie name km-tribe-session, 24h expiry.

Worth knowing

comparePasswords treats PIN 9999 (and, depending on stored format, 0000) as matching any stored hash — a second, implicit backdoor beyond the documented 9999 bypass. Also, two different code paths write localStorage['currentUser'] with slightly different field sets (Login.tsx vs use-auth.tsx's syncCurrentUserToLocalStorage) — worth consolidating if you're touching auth.

User Management

/users → client/src/pages/Users.tsx

Where every other page's access is actually decided. Create/edit staff records, assign a role, a department, which plants they belong to, which pages they can see, and which of those they can edit.

Admin-only — never grantable via Allowed Pages Table: users

How it works

  1. Table of all staff with search. "Add User" or the row's edit action opens the same form.
  2. Set Role (admin / super-admin / read-write / read), Department, Designation — these three still drive a handful of older, department-string-based checks on other pages (Load Operations, MP Operations, Print Operations' unlock logic, and parts of Proforma Slips).
  3. Plants — multi-select; which plants' data this person can see on plant-scoped pages (Overall Stock, Scan History).
  4. Allowed Pages — multi-select checklist, drawn from a single shared list (shared/pageKeys.ts). Checking a page here is what makes it appear in that user's sidebar at all.
  5. Write Access — a second multi-select, filtered to only the pages already checked above. A page can be view-only for someone even though they can see it.

API

GET/api/users
POST/api/users
PUT/api/users/:userCoderequirePageWrite("user-management")
DEL/api/users/:userCode

Key fields — users table

FieldTypeMeaning
userCodetext, PKStable identifier — used everywhere instead of the numeric id, including session serialization.
roletextadmin / super-admin / read-write / read. Admin & super-admin bypass allowedPages and pageWriteAccess entirely.
plantsjson textArray of plant names, e.g. ["VALSAD","INDORE"].

Worth knowing

user-management, settings, and activities are deliberately absent from the shared page-key list — they can never be ticked into anyone's Allowed Pages, admin-only by construction, not by a runtime check that could be bypassed by editing the array.

Order Scan

/scan → client/src/pages/Scanning/Scan.tsx

The floor app. Staff scan barcodes as boxes arrive against whichever CSV order is currently active for their plant; progress updates live for everyone watching the same session.

pageKey: scan-order Tables: orderScanItems, orderScanEvents

How it works

  1. When a CSV is active for the user's plant, the page swaps from a dashboard (recent scans, stats) into the live scan view automatically.
  2. Scan by camera, USB/Bluetooth barcode gun (HID keyboard-wedge — the page listens for fast keystroke bursts to tell a gun scan from someone typing), or manual entry with autocomplete.
  3. A matched barcode opens a confirm dialog showing the product photo, expected vs. already-scanned quantity, remaining boxes/pallets, and an STV selector if the plant uses one. Enter confirms; the qty/pallet fields convert into each other live.
  4. Scanning past what's expected logs the surplus as an Extra — a real, physically-received quantity, kept separate from the ordered amount rather than netted against it, and shown that way everywhere downstream (Overall Stock, reports).
  5. A barcode that matches neither the active CSV nor the product catalog is refused outright — "Barcode not in system" — rather than silently logged as an extra.
  6. If the same barcode appears on more than one order line, a picker dialog asks which line this scan belongs to before proceeding.
  7. Admin-only "Complete" closes out the part; a multi-part (FIFO) upload auto-advances to the next part for that plant once the current one completes.

API

POST/api/order-scan/sessions/:id/scansplits into an order-portion event (capped at expected) + an extra event
GET/api/order-scan/sessions/:id/items
GET/api/order-scan/sessions/:id/extras
GET/api/order-scan/sessions/:id/group-creditsFIFO cross-part credit, see Order Reports
POST/api/order-scan/sessions/:id/complete
POST/api/order-scan/events/:id/voidadmin-only, marks a mistaken scan without deleting it

Live updates broadcast over a WebSocket at /ws/order-scan, with polling as a fallback if the socket drops. On session completion, received quantities are written once to products.in_stock, the plant-wise product_plant_stock table, and an append-only stock_movements ledger — guarded so a retried completion can never double-count (server/lib/orderGroupReport.ts, applySessionStock).

Worth knowing

Product photos in the confirm dialog come from a local disk cache (server/uploads/product-images/), synced from Notion and looked up by product name rather than barcode — barcodes aren't guaranteed unique across distinct products in this catalog, but by the time the dialog needs an image, the exact line item is already resolved.

Overall Stock

/overall-stock → client/src/pages/OverallStock.tsx

The live, plant-wise stock ledger — what Order Scan sessions have actually produced, broken out by plant, with ordinary stock and over-order extras shown side by side rather than blended.

pageKey: overall-stock Table: product_plant_stock

How it works

  1. A configurable-column table — toggle Barcode, SAP Code, Category, Brand, Stock, Extra, Pallets, Extra Pallets, Last Updated on or off.
  2. Filter by plant and search by name/barcode; summary tiles up top total Stock, Extra (in both boxes and pallet-equivalents), and item count.
  3. Non-admins only ever see the plant(s) assigned to them; admins and super-admins see every plant with a plant filter to narrow it.
  4. Export the current view to CSV.

API

GET/api/scan-sessions/reports/plant-stockscoped server-side via getUserPlants(user)
Worth knowing

"Extra" is always the raw, physically-received over-order amount — it is never netted against a shortage elsewhere. FIFO credit adjustments (see Order Reports) change how a shortage is explained in a report, never what's actually sitting in this ledger.

Dispatch

/dispatch → client/src/pages/Dispatch.tsx

A single-purpose lookup-and-print tool: pull up one order by number, confirm vehicle/driver, print a QR-coded dispatch label for the truck.

pageKey: dispatch Source: Notion — no Postgres table

How it works

  1. Type an order number, search (or press Enter).
  2. Order details load from Notion — date, plant, status, party name/area/address/contact, invoice number. Vehicle/Driver and Invoice Amount are editable inline.
  3. "Print Dispatch" renders a plant-branded, QR-coded label (220×110mm) and sends it straight to the browser print dialog.
  4. Order not found shows a plain empty state with a "Try Another Order" reset.

API

POST/api/dispatchbody: { orderNumber }; requirePageWrite('dispatch'); reads live from Notion (DISPATCH_DATABASE_ID)
Worth knowing

Vehicle/Driver and Invoice Amount edits are local component state only — nothing is persisted. Refreshing loses them. There's also an orphaned duplicate handler at server/routes/dispatch.ts that's never actually mounted — the live route is dispatch-simple.ts.

Order Pipeline

Order Management

/order-import → client/src/pages/OrderImport.tsx

Where an order actually enters the system — an admin/billing user uploads the CSV(s) that Order Scan will later be run against.

Billing dept, or canAccessOrderManagement Write: admin/billing, or pageWriteAccess("order-import") Tables: orderImportSessions, orderImportItems

How it works

  1. Pick a Plant and an Order Date, then select one or more CSVs.
  2. Each file opens a column-mapping dialog — headers are auto-matched to Barcode / Item Name / SAP Code / Quantity / Expected Pallets (the parser scans the first 15 rows to find the real header, surviving pivot-table-style exports), reviewed, then imported one file at a time.
  3. Every CSV sharing the same Plant + Order Date is auto-grouped into one FIFO batch, ordered by upload sequence (receivingSessionId + partIndex) — this is entirely a server-side grouping, nothing the uploader has to configure.
  4. If the plant is idle, the first part auto-activates for scanning immediately; later parts wait and auto-advance as earlier ones complete.
  5. Sessions live in tabs — Available / Active / Completed / History — each with Load for Scan, Deactivate, Complete, Delete (soft-delete), and an expandable item list.
  6. The History tab shows each session's Started / Completed / Active For (from scanActivatedAt/scanCompletedAt) alongside its Part badge — the same timing surfaced in Scan Viewer's header and every Reports export.

API

POST/api/order-import/sessionsauto-groups by plant+date, auto-activates if the plant is idle
GET/api/order-import/sessions/:id/items
PUT/api/order-import/sessions/:id
DEL/api/order-import/sessions/:idsoft-delete; scan history for past reports is kept

Reports

Order Import → per-session "Reports" button → client/src/components/modals/ReportsDialog.tsx

What actually happened, after Order Scan ran — per-CSV and whole-batch reports, with the FIFO cross-part netting spelled out. Not a standalone page — opened as a dialog from a session row on the Order Management page.

Same gate as Order Management

How it works

  1. Opened per-session ("This CSV") and, when that CSV is part of a FIFO batch, also for the whole group ("Whole Order") — three report kinds either way: Summary (expected/received/extra/missing per item, FIFO-adjusted for groups), Activity (every individual scan event, in order), and Hourly.
  2. Hourly buckets that same scan-activity data into rolling 1-hour windows anchored to the session's actual scanActivatedAt — a 2:30 start produces "2:30 – 3:30", "3:30 – 4:30", ..., not clock-hour boundaries. Every window from start to the last scan appears even when empty, so gaps in scanning read as gaps, not missing rows. For a group, the earliest part's start anchors every part's windows onto one shared timeline. Voided scans and system credit-transfer rows are excluded from the totals (not real physical arrivals), same rule the Summary report's Received total already follows.
  3. Every report opens in-browser or downloads as CSV, Excel, or PDF. Hourly's in-browser view is its own expandable list — each hour collapses to a one-line count (scans/items/pallets) and expands to show its individual scans (time, barcode, item, scanned by, pallets, qty); a Download control sits inside that view too, and each expanded hour has its own "Download this hour" button for a single-window export.
  4. Summary, Activity, and Hourly all show Started / Completed / Active For (from order_import_sessions.scan_activated_at/scan_completed_at) as a header block above the report — per part for a group, so a multi-day FIFO batch's timeline is visible at a glance.

API

GET/api/order-import/sessions/:id/part-reportSummary
GET/api/order-import/sessions/:id/group-reportSummary, group scope
GET/api/order-import/sessions/:id/scan-activity?scope=part|groupbacks both Activity and Hourly — Hourly is bucketed client-side from the same event list, no separate endpoint

Summary/group figures are computed read-time, on demand, by server/lib/orderGroupReport.ts — computeGroupReport walks every part of a batch in sequence and nets an earlier completed part's leftover extra against a later part's shortfall for the same barcode, so a box that arrived early against the wrong part's CSV doesn't read as two unrelated discrepancies. It only reads orderScanItems/orderScanEvents — never rewrites them.

Scan Viewer

/scan-viewer → client/src/pages/ScanViewer.tsx

A read-oriented sibling of Order Scan — pick any plant and any order date, including already-completed ones, to see that order's scan progress without touching the live scanning session on the Scan page.

pageKey: scan-viewer Tables: orderImportSessions, orderScanItems (read-only)

How it works

  1. Header row: a Plant dropdown, the session's "loaded by" user, Started / Completed / Active For (from the session's scanActivatedAt/scanCompletedAt), a date picker, and — when a plant+date has more than one FIFO part — a part picker, all in one row, plus a progress bar / "Complete" badge.
  2. Same Master View (all parts for a plant+date merged, including Extras never on any CSV) and Part Order (per-file) views as the Scan page, re-implemented here read-only — no scan input, no camera, no keyboard-wedge listener.
  3. Item-history drill-down (who scanned what, when) for any row, same as Scan page's Master View.
  4. Void is available here too, gated by its own, narrower permission — see permissions-manual.html.

API

GET/api/order-import/sessions, /order-scan/sessions/:id/items, /extrassame read endpoints Order Scan's Master View uses
GET/api/order-import/master-view/item-history
POST/order-scan/events/:id/voidrequireVoidAccess — see permissions-manual.html
Worth knowing

This page duplicates a fair amount of Scan.tsx's merge logic (MvMergedItem) rather than importing it — the two files' comments cross-reference each other, so a fix to how Master View merges extras/credits in one almost always needs the same fix mirrored in the other.

Scan History

/reports → client/src/pages/Scanning/Reports.tsx

The full, flat audit trail of every individual scan event across every plant/order — searchable, column-filterable, exportable, and correctable (void) if a mistake was made. Distinct from the per-order Reports dialog above: this is one continuous log, not scoped to a single CSV or FIFO group.

pageKey: scan-history Table: scan_history (backed by order_scan_events)

How it works

  1. Backend-paginated (20/page) table — barcode, item, pallets/qty/loose, Extra/Empty-Box/Exchange flags, STV, scanner, order, plant, void status.
  2. Seven Excel-style per-column filters (STV, Time, Order Date, Plant, Barcode, Qty, Pallets), all enforced server-side via an explicit column allowlist (SCAN_HISTORY_FILTER_COLUMNS in server/routes/scan-sessions.ts) and persisted to sessionStorage so filters survive a refresh.
  3. Changing a filter or page resets to page 1 in the same render pass (not a follow-up effect), so switching filters can't briefly query with a stale page number against the new filter set. Auto-refresh (every 5s) only runs on page 1 — it's paused on later pages, since a live newest-first feed would otherwise shift every page's offset window under the reader mid-poll.
  4. Void and Excel/PDF export are both write-gated; void reverses the scan out of stock the same way the underlying /order-scan/events/:id/void endpoint always has.

API

GET/api/scan-sessions/reports/scan-historyLIMIT/OFFSET pagination + the 7-column filter allowlist above
POST/order-scan/events/:id/voidrequireVoidAccess — see permissions-manual.html
Worth knowing

The column allowlist is a deliberate safety pattern (an unknown filter id is silently ignored rather than passed to SQL), but that same silence previously let 3 of the 7 UI filter columns (Barcode, Qty, Pallets) go unenforced server-side for a while without anyone noticing the UI was filtering nothing — worth grepping SCAN_HISTORY_FILTER_COLUMNS against the client's filterable-column list if you add a new column here.

Catalog & Documents

Product Master (Notion Sync)

/notion-inventory → client/src/pages/NotionInventory.tsx

The product catalog itself — mastered in Notion, mirrored into Postgres. Every other module's idea of "what a product is" traces back here.

pageKey: notion-inventory Table: products

How it works

  1. A configurable-column product table, including a live thumbnail for each product's photo.
  2. "Check Sync" (Detect) does a dry-run diff against Notion, field by field, and shows what changed before anything is written; "Apply" commits it. "Auto Sync" applies automatically the moment a detect finds anything. "Full Sync" wipes and re-imports everything from scratch.
  3. A background job also runs this same detect-and-apply automatically — once shortly after every server start, then every 24 hours — so the catalog drifts back into sync even if nobody opens this page.
  4. CSV import is also available as a manual fallback path, independent of Notion.

API

POST/api/notion-inventory-sync/detect
POST/api/notion-inventory-sync/apply
POST/api/notion-inventory-sync/full-sync
GET/api/products/image-by-name?name=serves the cached photo; disambiguates by name since barcode isn't always unique

Images are the one field synced outside the normal text diff — Notion re-issues a fresh, expiring URL for a hosted file on every fetch, so comparing it as text would falsely report a change every single run. Instead: download once, resize to fit 600×600 and re-encode as JPEG, hash the result, and only touch disk/DB when that hash actually changes. Cached locally at server/uploads/product-images/<id>.jpg, served with an ETag so a browser that's already seen a product's photo never re-fetches it.

Proforma Slips

/proforma-slips → client/src/pages/ProformaSlips.tsx

Order slips, printable and lockable once printed — the same lock/unlock pattern as Print Operations, on a different document type.

pageKey: proforma Write: pageWriteAccess("proforma"), or IT/Management dept, or Billing+Head

How it works

  1. Search or browse slips; add new items via the search-and-add panel (Add/Edit gated by write access).
  2. Print locks the slip automatically — this auto-lock deliberately only needs read access to Print Operations and Proforma (not write), so a view-only print user's slip still locks behind them. Unlocking it again needs write access and (independently) one of: IT department, Management department, or Billing department with Head designation. See permissions-manual.html for the exact rule.
  3. Slips can also be pulled in directly from Notion via the Import dialog.
Worth knowing

Add/Edit access is a clean per-page grant (hasPageWriteAccess("proforma")). Lock/unlock deliberately keeps its older department-based conditions alongside the new grant rather than replacing them — both paths work.

Print Operations

/print-operations → client/src/pages/PrintOperationsFinal12.tsx

Search an order, print it, and manage the print-lock that stops the same order being reprinted by accident.

pageKey: print-operations

How it works

  1. Search by order number; the located slip prints directly, with a running print count and locked-after-first-print behavior when the plant has locking enabled. The lock this fires is read-gated, not write-gated — a user with only view access to Print Operations and Proforma can still print and have it lock correctly (a toast now surfaces if that lock call fails for any reason, instead of only a browser-console error).
  2. Unlocking a locked slip needs: admin/super-admin, IT department, Management department, Billing+Head designation, or a per-page write grant.
  3. Admins get a "Plant Management" shortcut button straight from this page.

Settings

/settings → client/src/pages/Settings.tsx

A tabbed settings page where roughly half the controls are wired up and half are visual placeholders — worth knowing which is which before you go looking for a bug in one that was never connected.

pageKey: settings — viewable by any grant, mutations write-gated

What's actually real

  1. Voucher Prefixes (Application tab) — the text prefix stamped on new Expense/Toll vouchers. Genuinely persisted.
  2. Clear Inventory / Reset Stock Values (Data Management tab) — real, destructive, and gated behind a confirm dialog that requires typing CLEAR plus an acknowledgement checkbox.

What isn't

The Scanner tab (camera flash, continuous scan, barcode type toggles) and the rest of the Application tab (dark mode, notifications, language) have no save handler at all — flipping them changes nothing. Same for "Clear Scan History," "Reset Application," and the Export/Import buttons in Data Management.

API

GET/api/voucher-prefixespublic, no auth
PUT/api/voucher-prefixes/:typeadmin, or pageWriteAccess("settings")
POST/api/products/clearrequirePageWrite("settings")
POST/api/products/reset-stockrequirePageWrite("settings")

There's no dedicated settings table — the real state here lives in voucherPrefixes plus direct mutations against products.

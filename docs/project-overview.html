KM Finny is a warehouse & dispatch operations system for a multi-plant FMCG distributor.

It runs the whole physical flow of a delivery: a CSV order comes in, warehouse staff scan boxes against it as they arrive, stock totals update live per plant, and the paperwork that goes with a shipment (proforma slips, dispatch labels, vouchers) gets generated and printed along the way. Everything is scoped by plant (a physical warehouse location — Indore, Valsad, Rajkot, …) and, as of the most recent addition, by the Indian state each plant is in, since pricing and pallet configuration are really state-level facts, not plant-level ones.

React + Vite Express + Node PostgreSQL + Drizzle ORM WebSockets Notion (product catalog source)

What this is

One system covering the whole path from "an order lands" to "the truck is dispatched with the right paperwork."

  1. A CSV order (one file per part of a delivery) gets uploaded on the Order Management page. Each session's own Reports dialog (Summary / Activity / Hourly) becomes available as soon as scanning starts producing data — Hourly buckets scans into rolling 1-hour windows from the session's real start time, expandable per hour and downloadable whole or one hour at a time.
  2. Warehouse staff scan barcodes against it on the Scan Order page as boxes physically arrive — the system tracks Expected vs. Received vs. Extra per item, in real time, across every device scanning against the same order.
  3. Scan Viewer is a read-only sibling of Scan Order — pick any plant and any order date, including already-completed ones, to see that order's scan progress without touching live scanning. Void is available there too, but only under its own, separately-granted permission.
  4. Overall Stock shows the live, per-plant running stock total that every scan feeds into, alongside what was ordered (Expected) and what's actually been sold (Sale, from Proforma Slips) for the same barcode.
  5. Proforma Slips and Print Operations generate and lock the dispatch paperwork for a completed order.
  6. Scan History is the full audit trail of every individual scan — searchable, exportable, and correctable (void) if a mistake was made.
  7. Product Master is the catalog everything else reads from — mirrored from Notion, the actual source of truth for product data.

See field-manual.html for a full page-by-page reference of all of this, including every API route each page calls.

Architecture

One server process, one Postgres database, one WebSocket channel layered on the same HTTP server — no separate services to deploy.

  1. The Express app (server/index.ts → server/routes.ts + server/routes/*.ts) serves the JSON API under /api and, in production, the built React app for everything else.
  2. Every request that needs to know "who's asking" goes through the same Passport session — including the WebSocket upgrade handshake, which manually replays the session/passport middleware chain (see server/routes/order-scan.ts's initOrderScanWs) since the ws library doesn't run Express middleware on its own.
  3. Drizzle ORM defines the schema once (shared/schema.ts) and is used both for typed query building and for inferring the Zod validation schemas API routes use.
  4. Schema migrations are mostly applied as idempotent ALTER TABLE ... IF NOT EXISTS statements run automatically on server startup (see the top of server/index.ts), rather than a strict migration-file-per-change workflow — pragmatic for a single-environment deployment, worth knowing before assuming a missing migration file means a missing column.
  5. Product data doesn't originate in this app — server/services/notionInventorySync.ts pulls it from Notion (Detect → review → Apply, plus an automatic 24h background sync), with a manual CSV import as a fallback path.

The Domain

The core pipeline

Everything in this app hangs off one linear flow, with one important twist: an order can arrive as several CSVs ("parts") over time, and they all need to reconcile against each other.

Order Import (CSV)→ Order Scan (barcode receiving)→ Overall Stock (live totals)→ Proforma / Print (dispatch docs)

FIFO parts & groups

  1. A single physical order can be split across several CSV uploads over multiple days (a "multi-part delivery") — each upload is a part, numbered in upload order, sharing one group (same plant + order date).
  2. Every part in a group is scannable simultaneously — a scan searches the whole group in part order to find which part a barcode actually belongs to, not just whichever part happens to be "active."
  3. When a part is marked Complete, any leftover over-scanned ("Extra") boxes on it automatically credit forward to a later part's shortfall for the same barcode — see reconcileCredits in server/lib/orderGroupReport.ts. Voiding a mistaken scan can similarly backfill a shortfall from leftover Extra on the same item.
Worth knowing

"Extra" means over-received relative to what the CSV expected, not a separate product concept — the same barcode can have both a Regular (order-matched) total and an Extra total, tracked and displayed separately throughout Scan Order, Scan History, and Overall Stock.

Plants, states & products

The newest layer of the domain model — worth understanding since it changed how several pages resolve data.

  1. Plants (Plant Management page) are physical warehouse locations. Each one now also carries an Indian state code (e.g. GJ, MP) — set on the Plant Management form.
  2. Products (Product Master, mirrored from Notion) carry state-specific data: pallet size (gjPlt/mpPlt) and a block of GJ/MP/UP pricing and tax reference fields — both keyed by state, not by plant.
  3. Any page that needs a product's pallet size for a given plant resolves it in two steps: plant → its state (via the Plants table), then state → the product's value for that state. This replaced an earlier version that guessed the state by string-matching the plant's name (e.g. checking if the name contained "valsad") — fragile once more than two plants/states are in play.
Worth knowing

Two plants in the same state intentionally share the same pallet-size and pricing data — that's the model working as designed, not a limitation to route around.

Stock reporting: Total, Expected, Received & Sale

Overall Stock now reads from three different sources of truth at once, not just the live running stock table.

  1. The page's top-level tabs switch on state, not plant — a state with more than one plant under it (e.g. GJ: Rajkot, Valsad, Baroda) shows their stock combined by default, with a second, nested pill row to narrow down to one specific plant. A single-plant state (MP: Indore) has no nested row, since the state view already is that one plant's view.
  2. Expected Qty sums ordered quantity from order_import_items/order_import_sessions (the CSV import pipeline) — an all-time sum by default, or scoped to one order date when a date filter is picked.
  3. Received Qty/Extra come from the live per-plant running totals (product_plant_stock) that every scan feeds into — Received is every physical box counted (extras included), Extra is just the over-order portion of that, shown separately.
  4. Sale Qty is new: a sum of Proforma Slip quantities for the same barcode+plant, matched by the slip's own order date the same way Expected Qty is. Unlike Expected Qty's true all-time default, "all dates" here floors at a fixed start date (sales tracking isn't considered reliable before then) — see SALES_TRACKING_START in server/routes/scan-sessions.ts.
  5. Total Stock (the first data column, right after Plant) is a derived reconciliation figure: Extra + Received − Sale, with its own pallet-equivalent shown inline in the same cell rather than as a separate column.
Worth knowing

Every pallet figure on this page (Expected/Received/Sale/Extra/Total Pallets) is computed per-row, using that row's own item-per-pallet size — never one blended pallet size applied across every row, same rule used everywhere else in the app.

Users & permissions

Two-tier per-page grants, plus a couple of narrower rules layered on top for specific actions.

  1. Every user has a View Access and Write Access list (page keys), set on the Users page. Admin/super-admin bypass both, everywhere, unconditionally.
  2. A handful of actions use different rules entirely — a designation blocklist for who can mark an order Complete, and a dual-page-AND rule (write access to two different pages at once) for a couple of sensitive actions like Print Operations' Unlock and Void.
  3. Scan Viewer's own Void action takes this further with an OR-of-ANDs rule: admin, or Write Access to both Scan Order and Scan History (the existing combination), or Write Access to Scan Viewer alone — so someone can be trusted to look up and correct a mistake there without getting full access to the real Scan Order page. See requireVoidAccess in server/routes/order-scan.ts.
  4. Plant scoping is a separate, independent check layered on top for Order Management and Scan Order — a page-level grant says nothing about which plant(s) it applies to.

Full button-by-button and route-by-route detail: permissions-manual.html.

Running it locally

Short version — full step-by-step (including PostgreSQL setup and default login) is in LOCAL_SETUP.md at the repo root.

  1. npm install
  2. Set DATABASE_URL and SESSION_SECRET in a .env file (see LOCAL_SETUP.md for the exact format).
  3. npm run db:push — applies the Drizzle schema to your database. (Most of the day-to-day incremental changes since then run automatically as startup migrations in server/index.ts, not through this command.)
  4. npm run dev — starts the server with hot reload at http://localhost:5000 (or your configured PORT).
  5. Emergency admin login: PIN 9999.

The Mechanism

read this first

How permissions work

client/src/lib/permissions.ts + server/lib/pageAccess.ts

Two JSON columns on the user record, one helper pair per side, and admin always wins. Everything else in this document is a variation on this.

The two grants

  1. View Access (allowedPages) — can open the page at all. Checked by hasPageViewAccess(pageKey) on the client, requirePageAccess(pageKey) on the server.
  2. Write Access (pageWriteAccess) — a subset of View Access; can actually change something on that page. Checked by hasPageWriteAccess(pageKey) / requirePageWrite(pageKey).
  3. Both are set per-pageKey on the Users page — the list of grantable keys and their display labels lives in shared/pageKeys.ts (CONTROLLABLE_PAGES), which is also what drives the checkbox labels on that page.
  4. Admin / super-admin bypass everything, on both sides, unconditionally — a grant is never checked for these two roles.

Client vs. server — read separately, on purpose

hasPageWriteAccess/hasPageViewAccess read localStorage.currentUser, kept in sync by client/src/hooks/use-auth.tsx's AuthProvider (refetches /api/user on window focus and every 60s). This is what decides whether a button is hidden. It is advisory only — a determined client can always call the API directly. requirePageWrite/requirePageAccess on the server are the actual enforcement: they read the SAME two JSON columns fresh from the authenticated session on every request. A page is only really protected where a server guard exists — several routes below are annotated no server guard for exactly this reason; they rely entirely on the client hiding the button / the route guard on the page itself.

The three rule shapes actually in use

  1. Plain gate — admin, or Write/View Access to one specific pageKey. The default; most buttons and routes below are this.
  2. Dual-AND gate — admin, or Write Access to two different pageKeys at once, chained as two separate middleware calls server-side (each is its own check in the route's middleware list, so both must pass — passing an array to one call is OR, not AND). Used for Print Operations Lock/Unlock and Scan Order/Scan History's Void.
  3. Designation blocklist — nothing to do with View/Write Access at all: admin, or the user's designation (Loader/Helper/Driver/Scanner) is NOT in a fixed blocklist, exact match. Used only for Complete (Order Management and Scan Order).
Worth knowing

Plant scoping is a fourth, orthogonal axis layered on top of all three shapes for Order Management and Scan Order specifically: getUserPlants(user) (in server/routes/order-scan.ts) returns null for admin/super-admin/billing (unrestricted) or the user's real users.plants array otherwise — an empty array fails CLOSED (no plants assigned = no access), not open. A page-level Write Access grant says nothing about which plant(s) it applies to; both checks run independently.

User Management

/users → client/src/pages/Users.tsx

Where every grant described in this document actually gets set. Admin-only to open at all.

Admin/super-admin only — hardcoded, not grantable

How a grant is made

  1. Per user, per page: a View Access checkbox and a (dependent) Write Access checkbox, one row per entry in CONTROLLABLE_PAGES (shared/pageKeys.ts). Write Access implies View Access is expected to be on too, but the two are stored as independent JSON arrays — nothing stops View from being off while Write is on beyond the UI's own convention.
  2. Designation is a separate field entirely (Director/Manager/.../Loader/Driver/Scanner/...) — it feeds the designation-blocklist rule above, never the page-grant system. Changing a user's designation can silently change their Complete rights without touching either checkbox.
  3. Plants assigned to a user (multi-select) feed getUserPlants — separate again from both page grants and designation.
Worth knowing

The "Scanner" designation is the one deliberately overloaded case: it's simultaneously a Complete-blocklist entry AND the sole trigger for the Dispatch-style read-only dashboard view on the Scan page (isDispatchUser) — see Scan Order below.

Worth knowing

requireOrderImportWrite (and every other write route above) also checks getUserPlants against the session's own plant — a Write Access grant alone does not let someone activate/complete/reopen a session outside their assigned plant(s). Complete deliberately ignores Write Access altogether: a user with zero Order Management grants but a non-blocklisted designation can still Complete a part, and conversely a user with full Write Access but designation "Loader" cannot.

POST /order-scan/events/:id/void chains two requirePageWrite calls — 'scan-order' then 'scan-history' — as separate middlewares, which is what makes it AND rather than OR. Voiding also auto-backfills a resulting shortfall from any leftover Extra on the same item (own bookkeeping, not a permission concern, but changes what a void actually does server-side beyond the obvious).

Worth knowing

Unlock needs BOTH grants because it's really two different permissions being asked at once — "can operate Print Operations" and "can modify a Proforma Slip" — and the feature happens to sit on the print-operations page while mutating a proforma record. A user with only one of the two grants sees a fully clickable Unlock button that would 403 on click if the client check weren't kept in sync with this exact server rule.
